# 2026-08-19 工作日志

## 服务停止逻辑设计重构（P0）

**触发**：用户报"停止失败: 端口 80 仍被进程 408 占用"

**根因诊断**：
- 进程 408 是本实例 nginx，但 taskkill 兜底重试 3 次都失败
- `process.Manager.Stop` 注释写 `taskkill /F` 但实际用 `os.FindProcess().Kill()`（单进程 TerminateProcess，不杀子进程）
- nginx master+worker，杀 master 不杀 worker，worker 拖留占端口
- `manager.go:479` 调用 `m.procMgr.Stop(pid)` 完全吞掉 error，权限不足也无感知
- provider.Stop 全部直接 `proc.Kill()`，无服务自带优雅停止命令 → MySQL/Redis 强杀有数据损坏风险
- service.Manager 叠加端口扫描兜底判据，与 provider 的"进程退出"判据冲突
- `stopOwnedProcessByPort` 创建新 Manager 实例杀进程，与 `i.pm` 不是同一注册表，且边收集边杀

**设计决策**（参考 ServBay/XAMPP，用户拍板"设计重构"）：
- 分层停止：优雅停止（服务自带命令）→ 等进程退出 → 兜底 `taskkill /F /T`
- 进程所有权：用 `ownedPIDByPort`（只收集 PID 不杀），统一在 provider.Stop 内杀
- 统一判据：进程退出，不用端口释放（端口可能被外部占用 / TIME_WAIT）
- 错误透传：捕获 taskkill stderr，真实失败原因（access denied 等）带给用户

**改动文件**：
- `internal/process/process.go`：`Manager.Stop` 统一 `taskkill /F /T` + 捕获 stderr + 已退出幂等 nil
- `internal/provider/stop.go`：删 `stopOwnedProcessByPort`（设计缺陷），加 `runStopCommand` 辅助
- `internal/provider/nginx_provider.go`：Stop 加 `nginx -s stop` 优雅层（复用 reloadCommand 模式，依赖 `logs/nginx.pid`）
- `internal/provider/mysql_provider.go`：Stop 加 `mysqladmin --port=<p> -u root shutdown`（避免强杀数据损坏），等 10s
- `internal/provider/redis_provider.go`：Stop 加 `redis-cli -p <p> shutdown`（触发 RDB save），等 8s
- `internal/provider/php_provider.go`：php-cgi 无自带停止命令，直接 `taskkill /T` + 等退出
- `internal/service/manager.go`：Stop 删端口扫描兜底（454-512），信任 provider 返回，stopErr 透传

**验证**：`go build` ✓ / `go vet` ✓ / service+process+provider 测试全过

**遗留**：
- GUI 未分离 stop/kill 交互（ServBay 模式），当前靠 provider 内部分层兜底
- 未引入显式 PID 文件管理（nginx 已有 `logs/nginx.pid`，mysql/redis 靠端口反推，可后续优化）
