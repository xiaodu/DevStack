# 环境/组件启停 —— 遗留问题记录

> 2026-10-15。记录本轮 UI 反馈暴露的问题：哪些已改、哪些是还没啃的硬骨头。
> 关联总方案：`docs/核心体验改进方案.md`（尤其「六、贯穿性架构建议」1/2 条）。

## 一、已修复（本轮提交）

### 1. 术语/语义混乱（`ea63709`）
现象（用户反馈）：
- 环境管理按钮叫「激活」，但激活后在 Dashboard 点"启动"图标却提示"正在激活环境"；点"停止"又叫"正在停止全部组件"。
- 冷启动有激活环境时点启动又叫"启动「LNMP」"。
- 无运行组件时点停止提示"没有正在运行的**服务**"——一会儿"组件"一会儿"服务"。

根因：两个层级（环境级 / 组件级）的操作词混用，且 Dashboard 顶部绿色按钮**实际调的是 `activateEnvironment`（激活=切当前+启全部）**，却长着"启动"图标。

定稿的模型：
- **环境级**（只在「环境」页做）：`激活`=设为当前并启动全部组件；`停用`=停止全部并取消当前。
- **组件级**（Dashboard 顶部 + 各组件页）：`启动` / `停止`。
- 组成环境的部件**一律叫「组件」**（不再用"服务"）。
- Dashboard 顶部绿色按钮 = **启动当前环境的组件**（改调 `runEnvironment`，不切环境）；红色 = **停止当前环境的组件**。

### 2. 装完不即时刷新（`ea63709`）
现象：安装完成后，Environment 页的"已安装/激活"按钮要切走再进来才更新。
根因：安装完成走 `download:phase` 的 `done` 事件，没触发 `refreshSignal`；且 `installStatus` 是普通 `let` 非 `$state`。
修复：`events.ts` 监听 `download:phase` 到 done/error 时 bump `refreshSignal`；`installStatus` 改 `$state`。

### 3. 停止假失败（`854f788`）
现象：`停止失败: 进程 PID 8624 仍在监听端口 80`。
根因：`stopServiceByName` 每次 `NewInstance` 造一个**不认识当前活 PID** 的新实例，只能靠"扫端口反查单个 PID"去停，nginx 的 worker/孤儿易漏杀；复核（P0#9 的诚实化）如实逮到进程还在 → 报失败。
本轮缓解：复核命中占用进程时，先 `taskkill /F /T` 兜底强杀 + 等端口释放（≤2s），仍不干净才报错。

## 二、遗留硬骨头：启停控制流仍是三层，未真正"单一真相源"

**状态展示层已统一**（不撒谎、端口/进程复核、5s 周期调和 `StartBackgroundSync`、事件丢弃 `reactive:overflow` 兜底）——上面第 3 条能报出"仍在监听"正是它在起作用。

**但启停的控制路径还是碎片化的**，一次 `Stop` 要穿过三层，每层各记各的 PID/端口：

```
service.Manager.Stop(id)            internal/service/manager.go:618
  └─ orchestrator.Engine.Stop(id)   internal/orchestrator/engine.go:554   （自己快照 svc.PID、markStopped、等 isPIDRunning）
       └─ stopFunc → stopServiceByName(name)  internal/service/manager.go:237
            └─ provider.NewInstance(...) 造新实例 → entity.Stop()  internal/provider/nginx_provider.go:384
                 （i.pid=0，靠 ownedPIDByPort 扫端口反查 PID）
```

问题点：
- **PID 记账重复且口径不一**：service 层有 `s.process.PID`，orchestrator 有 `svc.PID`，provider 实例又独立一份（且 Stop 时是 0）。三方对不上时就要靠"扫端口"兜底。
- **`stopServiceByName` 用 fresh 实例**（manager.go:260 `p.NewInstance`），不携带活 PID，是漏杀的根源。
- **orchestrator 对内置服务基本是空壳**：内置服务经 `RegisterService(name,"",nil,...)` 注册，Command/Args 为空，orchestrator 的 `svc.PID` 常为 0，`markStopped` 的 `isPIDRunning(0)` 恒 false → 它其实没真正管进程，真正的启停在 provider。orchestrator 这层对内置服务是冗余的。
- 内置服务（nginx/mysql/redis/php）走 provider，而 php/node 运行时又走 `runtime.Manager`，两套启停并存。

**目标重构（对应总方案六.1/六.2）**：
1. **provider 持有活 PID**：`Start` 成功后 provider 实例记录真实 PID；`Stop` 直接用该 PID + 杀全部匹配端口的本目录进程树，不再靠"扫端口反查单个 PID"。
2. **单一状态真相源**：`service.Manager` 的实例状态 + 5s 调和快照作为唯一事实；`orchestrator.Engine` 对内置服务退化为纯转发（或移除内置服务在 orchestrator 的记账），去掉三层重复。
3. **启停入口收敛**：`Stop(id)` 只有一条落地路径（provider.Stop / runtime.Stop），复核与兜底强杀合并进 provider，别在 service 层再补一遍。

风险：触及 orchestrator/engine.go、service/manager.go、各 provider 的实例生命周期，需配合现有 `reconciler`/`watchProcess` 回归测试；建议单独一轮做，先补测试再动。

## 三、其它小尾巴
- 顶部绿色按钮改用 `runEnvironment` 后：若激活环境的组件"部分已启动"，`RunEnvironment`→`reconciler.Run` 需确认对已运行组件是幂等跳过（避免重复启动报错）。待验证。
- `activateEnvOnly`（仅切激活标记）与 `activateEnv`（切+启）在「环境」页文案都叫"正在激活「name」"，可再细分措辞。
